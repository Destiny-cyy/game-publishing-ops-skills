# 复盘 / 整理 / 总结 弹性流程

## 定位

把复盘、整理、总结类任务按一套**弹性框架**推进：先判断，再按需选动作，收口即进下一段。
本文件不是逐条照做的检查表。除「三条底线」外，动作均可按任务实际情况裁剪、合并、跳过；
判断空间是本技能的一部分，不要把本框架再固化成强硬的编号步骤。

## 何时加载

用户说「复盘」「整理」「总结」，或意思相近的话（回顾、梳理、汇总、沉淀经验等）时加载。
任务很小、资料很少时仍可加载，但允许把流程压缩成一两轮。

## 三条底线（唯一写死的地方）

1. **先对齐**：动手前把已定过的结论、记录、口径摆出来对一遍，确认这轮和以前说的是同一件事、同一套说法；对不上的先标出来，不闷头各写各的。
2. **每步留痕**：每条结论、每个数字都能追回出处（来自哪份资料、怎么取的、是否加工过）；加工过的保留中间产物，不覆盖、不凭记忆复述。
3. **删前先问**：反复核实确认某条归档信息无用后，先列出要删的、向用户确认，得到同意再删；实体文件一律不直接删，只进回收站。

## 开始前先判断（决定这轮跑多重）

不套固定档位，按现场情况判断：

- 任务规模与资料量：决定跑几轮、要不要建完整资料地图。
- 有没有已有结论或口径需要先对齐，对不上的有多少。
- 有没有能拆开并行处理的块：据此决定要不要派多个子 agent（允许、非必须）。
- 范围是否清楚：不清楚就先确认范围，别默认「全都要」。

判断完再决定启用下面哪些动作、按什么顺序。资料少、任务小可压缩成一两轮，但三条底线不省。

## 可裁剪动作清单（按需取用，不强制顺序）

### 对齐既有口径
摆出既有结论、记录、口径逐条比对；标出冲突点，先处理冲突再往下走。

### 总结经验并选最优路径
不只写「发生了什么」，还要给出「下次走哪条路最省事、最稳」的一条明确推荐，并说明别的路为什么不划算。
严格区分事实、推测、主观判断，分别标注。

### 清理内容：两类都剔
- 前后对不上、自相矛盾的 → 剔掉
- 为凑篇幅硬塞、东拼西凑、没有信息量的 → 剔掉

只留能对齐、有出处的内容。剔掉什么在留痕里记一笔，不悄悄抹掉。

### 整合资料：沿用「不通读」老规矩
整合、汇总一批资料时走：不要通读 → 先建地图（只登记元信息）→ 按需取用 → 每步留痕。
完整做法在用户级规矩本子的 `memory/rules-material-integration.md`（与 `MEMORY.md` 同一目录下的 `memory/` 子目录）。
此处只挂接，不复制正文、不另起一套。

### 归档收口
结论定稿后归档。已归档信息反复核实确属无用的，按「删前先问」底线处理。

### 分头推进与合稿
任务够大、且存在可并行拆开的块时，派多个子 agent 分头处理（允许、非必须）。
分头最容易各写各的、口径对不上，因此**合稿前必须先互相对齐再收口**；每块产出都要带出处。

### 收口后进入下一阶段
上一段收口即自动进入下一段，不停下来等确认。
例外：要删东西、范围明显说不清 —— 这两种情况先问用户。

## 与其他规矩的关系

- 全局“文件删除规则”“不修改原表”“往公开仓库发布前先审后传”等红线照常生效，与本技能叠加、不互相覆盖。
- 本技能的「删前先问」与全局删除规则一致，不得因阶段自动推进而绕过。
- 阶段自动推进 ≠ 可以跳过对齐，也不等于可以自作主张删东西。

## 自适应留白

- 本清单是起点不是终点：遇到没覆盖的情况，按目标自行补动作并留痕，不硬套步骤。
- 将来若拿到历史聊天记录或新的真实用例，按需把具体做法补进对应动作，不改整体框架。
- 若经验证说「不走流程 / 直接改」，尊重用户，跳过本框架。
