# 复盘与决策

> **场景自适应（v2.0，{{AS_OF_DATE}}）**：复盘时先确认本期用的是哪个场景档，口径与基线的可比范围以档为准；硬红线（不可比口径不相加 / 证据等级 / 归因与相关性区分）不随场景变。见 `_shared/规则三层说明.md` 与 `../REDLINES.md` 第零章。

复盘的价值不在报告，在于**产出一个明确的下阶段决策**，并把学到的东西沉淀回上下文与活动基线。

## 开工前

读 `_shared/context-template.md` 第 6 节（统一口径）。口径不统一，复盘就是吵架。

## 一、统一口径回收（强制）

**可比口径清单从本期场景档 `metrics.comparable` 取，件数不是规定**（{{AS_OF_DATE}} 修订）。复盘前先确认本期用的是哪个档——口径与基线的可比范围以档为准，别拿 A 档的「预约跳转」去要求 B 档的「一键入库人数」。

默认档（{{CHANNEL_TYPE_A}}·预约期）常见几项的定义：

1. **活动参与人数** —— 按渠道自有口径，**不要求去重**、分渠道单列
2. **加速人数环比（%）** —— 活动期 ÷ **活动前两周日均** − 1（分母避开前置活动收官周）
3. **入库任务完成率** —— 完成「一键入库」任务的人数 ÷ 活动参与人数。**现行口径改为「页面点击率」**：点击率的分母（活动页访问）{{CHANNEL_COUNT}}家定义不一，且按钮放第几屏可直接操纵 CTR；入库完成率{{CHANNEL_B}}一直回传，历史 {{BASELINE_COMPLETION_RATE}}、中位 {{BASELINE_MEDIAN}}。证据等级 B 级 · 首期基线。
4. **回归人数** —— 渠道侧可算，单独报数

**曝光率（资源位曝光达成率 = 实际 ÷ 承诺）是履约层、不是效果 KPI**，只用来验证渠道是否给足资源位，不作结案依据。

**参考项**（不得作结案依据）：曝光量、点击、PV、抽奖人次、互动、KOL 播放量。

**回写基线时，本期首次统计的指标要单独标注「首期、无基线」**，不要拿首期数字直接当基线用。

⚠️ **绝对禁止**：把不同渠道口径不同的数字直接相加或横向比较。
{{CHANNEL_D}}报点击、{{CHANNEL_A}} 报 push 曝光、{{CHANNEL_B}}报 PV/UV、{{CHANNEL_C}} 报抽奖人次、{{CHANNEL_E}}报入库——**这些不是同一个东西**。
要相加就必须先换算到统一口径，换算不了的单独列、单独说。

## 二、历史基线（用于判断「好还是不好」）

> 这一节**必须自己填**，包内不预置任何真实数字。基线只作参照、不是验收阈值；每个值都要带「统计区间 + 口径 + 证据等级（A/B/C）」。

**填表模板**（建议维护在 `_shared/context-template.md`，逐期累加）：

| 渠道 | 曝光级 | 参与级 | 转化级 | 统计区间 | 口径定义 | 证据等级 |
|---|---|---|---|---|---|---|
| {{CHANNEL_A}} | {{BASELINE_REACH_A}} | {{BASELINE_PARTICIPATION_A}} | {{BASELINE_CONVERSION_A}} | {{BASELINE_PERIOD}} | {{METRIC_DEFINITION}} | {{EVIDENCE_LEVEL}} |
| {{CHANNEL_B}} | … | … | … | … | … | … |

**三条填写纪律**
1. 本期首次统计的指标单独标「首期、无基线」，不要拿首期数字当基线。
2. 不同渠道口径不同的数字**不相加、不横比**；要比较先换算到统一口径，换算不了的单独列、单独说。
3. 基线的价值是解释波动，所以每个异常值旁边记一句「当时发生了什么」，否则下期无法归因。

**必记的三个结构性字段**（经验证最能解释波动）：
- 转化任务所在的屏位 / 是否首屏前置
- 是否有独立入口与定向触达
- 渠道实际给到的资源位是否达标（履约层，不是效果 KPI）

## 三、归因纪律

- 明确区分「归因明确」（有追踪链路）与「相关性推测」（时间重合）
- 多渠道同日上线时，不许把增量全算给某一家
- 样本量不足标"待验证"，不写进决策依据
- 每个数字旁标注来源与口径

## 四、三层结论

1. **渠道层**：哪个渠道的人群重合假设被验证/证伪
2. **机制层**：任务链路哪一档转化最好（关注/入库/加速，通常加速最难但最真）、奖品档位是否匹配
3. **人群层**：我们对目标人群的哪个判断错了（这条最值钱）

每层写：原假设 → 实际 → 结论 → 下阶段怎么用。

## 五、决策（四选一，必须选一个）

- **继续**：当前层达标，进入下一层
- **加码**：超预期，提前升级或调资源
- **降级/改**：未达阈值，改人群、卖点或渠道后重跑 Smoke
- **砍掉**：触发 kill 标准，停止并记录原因

**不许出现"继续观察"这种没有截止条件的结论。** 要观察就写明观察多久、看到什么数字算过。

## 六、回写（比报告更重要）

1. 更新 `_shared/context-template.md`：渠道台账的历史表现、决策日志、版本号
2. **修正 `campaign-mechanic` 的基线数字**——预估基线要跟着真实数据走，不是一次性的
3. 修正 `channel-selection` 的打分——打分表要跟着真实数据走
4. 若结论推翻原假设，同步修正人群分层（L1–L4 的 CTR 参考值）
5. **回写准则文件 `_shared/REDLINES.md`**（准则层唯一真源）：
   - 新踩的坑 → **第八章**（表末追加编号，并判断属于 A~F 哪一类根因）
   - 新验证的基线 → **第十一章**（参与规模 / 曝光量级 / 加速环比 / 奖品价带 / CDK 库存水位）
   - 本期版本动作 → `{{VERSION_PLAN_FILE}}`
   - ⚠️ **改之前先 grep 现状**：该文件可能被云端预览手改或被其他会话覆盖，照着上一版记忆改必错

**六类根因归类（写坑时顺手标一下，方便下次统计）**：A 事实锚点 / B 口径 / C 活动设计 / D 奖品预算 / E 文档工程 / **F 交付形态**。
前两类是返工源（开始得太早），F 类是白交付源（方案对了但对方打不开 / 看不全）。
