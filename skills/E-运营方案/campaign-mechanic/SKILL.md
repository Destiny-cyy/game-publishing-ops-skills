# 渠道活动机制设计

这个 skill 沉淀的是使用方项目**已经跑通、被反复复用的活动骨架**。
从 {{VERSION_NAME_HIST}} 方案与历次奖励规划（{{VERSION_NAME_HIST}} / {{VERSION_NAME_HIST}} / 春节&安卓 / {{VERSION_NAME_HIST}}）提炼：四个渠道用同一套骨架，差别只在奖品包与任务细节。
**默认复用，不要重新发明。要改就在骨架上改，并说明为什么。**

## 开工前

读 **`_shared/REDLINES.md` 第五章（奖品与预算）**——奖品规则以它为准，两者冲突时改准则文件；再读 `_shared/context-template.md` 第 4 节（活动机制模板）、第 5 节（预算）、第 8 节（约束）+ `../REDLINES.md`。

问清：节点是什么、哪几个渠道、预算盘子、有没有 CDK 配额（需 {{APPROVAL_PARTY}}审批）、目标偏新进还是回流。

⚠️ **先定节点性质**：这个节点是**预约期 / 版本周 / 大版本周**？投入档位分别是上一版本节点的 **{{BASELINE_VALUE}} / {{BASELINE_VALUE}} / 另案（不低于上一版）**（准则 3.2）。性质定错，整套论证都要重写——曾因为「早期误写日期 版本日」其实是「预约开启日 预约开启 + 版本日 上线」，1.2 整节推倒重来。

⚠️ **先定四条约束再选品**：价带 / 份数结构 / 权重 / 红线。顺序反了必然返工——历史上一版方案因为先选了 {{BUDGET_AMOUNT}}~{{BASELINE_VALUE}} 的头奖再谈规则，整张奖品表推倒重做。
**先出「确认稿」（备选清单 + 分配草案 + 预算影响 + 待确认项），拿到明确答复后再写全文。**

## 一、任务链（由能力派生，件套数不是规定）

> 下表是**默认档（{{CHANNEL_COUNT}}家{{CHANNEL_TYPE_A}}·预约期）**的实例。按场景档 `channels[].capabilities` 生成：能关注才有关注任务、能一键入库才有入库任务、能加速才有加速任务、能跳外链且节点需导流才有跳转任务。{{CHANNEL_E}}无加速能力 → 没有加速任务与「加速福利」；{{SERVER_LINE_B}}不走 {{PLATFORM_A}} → 没有入库任务；版本周 → 没有预约跳转任务。

| 任务 | 用户动作 | 奖励 |
|---|---|---|
| **关注** | 关注{{CHANNEL_E}}官号 / 关注社媒账号 | 抽奖机会（或积分） |
| **入库** | 一键入库 / 平台入库 | 抽奖机会（或积分） |
| **加速 / 游玩** | 首次加速、加速达 X 分钟、每日加速 | **加速福利（渠道自有）** + 抽奖机会 |

**第四件（预约期专配，排在首屏第一格）：预约版本（点击跳转官网预约页）** —— 抽奖 ×2、**点击即计**。
三条插拔规则：① **点击即计，不要求完成预约登记**（登记率另作观测项）；② **必须排第一格**——它同时承担「导流到预约页」和「把参与门槛降到一次点击」两个作用，排第二格之后两个都失效；③ **移动端跨端要 H5 中间页**，别让用户直接跳浏览器。

**设计要点：**
- 三个任务对应三个深度——关注最浅、入库是中、**加速是真进入游戏**。奖励权重应递增。
- "加速福利"是**有加速能力的渠道**独有的杠杆：不花钱（渠道自有）、对用户是真价值。这类渠道每次活动都要用上；没有加速能力的渠道不硬凑。
- 回归任务（如"30 天未登录回归""新用户首次加速"）单独设档——对应 L1 回流人群，是效率最高的一层。**前提是渠道具备定向能力**（默认档只有{{CHANNEL_B}}有）；不具备就把回归目标降级为「单独报数、不作硬考核」。

### 渠道变体（默认档实例，换档按 capabilities 重生成）
- **{{CHANNEL_E}}**：H5 积分制。关注/入库/分享 → 积分 → 兑换奖品；配社区活动合集
- **{{CHANNEL_B}} / {{CHANNEL_A}}**：关注社媒 + 入库 + 游玩（加速）达时长 → 抽奖机会 & 加速福利
- **{{CHANNEL_D}}**：入库 + 首次加速 + 游玩（加速）达时长 → 抽奖机会 & 加速福利
- **{{CHANNEL_C}}**：PC+移动双端资源 + UP 主植入，另走 KOL 包

## 二、奖品结构（从场景档取，别把某一版定稿当基准）

> **基准随当期方案走**：本节的份数、价带、卡数一律从场景档 `prize.*` 取，下方表格只是「结构示意」，不是必须满足的数值。旧基准作废后不保留具体数字，避免误用。**价带、份数、权重一律从 `profiles/<id>.json` 的 `prize` / `weight` 取**，本 skill 不自带数字。

| 字段 | 含义 | 默认档取值 |
|---|---|---|
| `prize.model` | 奖池模型 | `lottery_tiers`；积分制 `h5_points`、平台奖励 `platform_reward` 会**整组关闭**价带/份数/权重检查 |
| `prize.bands` | 头奖 / 第二档价带 | 头奖 {{BUDGET_AMOUNT}}~{{BASELINE_VALUE}}、第二档 {{BUDGET_AMOUNT}}~{{BASELINE_VALUE}} |
| `prize.exceptions` | 登记在案的破例单品 | {{CHANNEL_D}} {{BUDGET_AMOUNT}}（鼠标品类 {{BUDGET_AMOUNT}} 带内无合适款，已在方案中确认） |
| `prize.structure` | 卡占比下限 / 每渠道头奖 / 第二档 > 头奖 | {{BASELINE_VALUE}} / ≥1 件 / true |
| `prize.count_by_budget` | 份数按盘子插值取档 | 盘子规模 → 头奖每渠道 1 件，第二档与卡份数按盘子插值 |
| `weight` | 顺序 / 同级容差 / 是否启用 | {{CHANNEL_A}} ＞ {{CHANNEL_B}} ≧ {{CHANNEL_C}} ＞ {{CHANNEL_D}}，差额 ≤{{BUDGET_AMOUNT}} |

**盘子变了结构就得变**（下面是结构示意，不是必须照抄的数值）：

| 盘子档位 | 结构示意 | 要注意什么 |
|---|---|---|
| 小盘子 | 头奖每渠道 1 件 + 少量第二档 | 中奖面低，参与感弱 |
| 中等盘子 | 头奖份数不变、第二档份数增加 | 第二档份数必须多于头奖份数 |
| 大盘子 | 头奖品类铺开 + 卡为主体 | 先看结构占比，别先砍卡 |

**结论**：盘子变了结构就得变。**先按盘子取结构档，再填单品**；结构比单项优先级重要。

### 五条红线（选品时逐条过）

1. **不得是任何已有 IP 的联动款**（联名款、限定联名一律不进奖池）。厂商自家配色 / 平台硬件授权不算联名，可用，但要写明豁免理由，避免反复审校。
2. **单价按电商实际成交价上浮 {{BASELINE_VALUE}}~{{BASELINE_VALUE}} 预留**（留议价空间，也防涨价）。
3. **品类铺开**：外设 / 音频 / 桌面生态分开，别清一色键鼠；**不撞款约束从场景档取**——默认档只约束「头奖」{{CHANNEL_COUNT}}家品类互异，同款可跨渠道出现，禁止的是同一渠道内部同款。
4. **头奖单价不往上推**（守住场景档 `prize.bands.头奖` 带，默认档 {{BUDGET_AMOUNT}}~{{BASELINE_VALUE}}，破例登记在 `prize.exceptions`）。要加吸引力就**换品类 / 加份数**，不是加单价。仅 `lottery_tiers` 场景适用。
5. **第二档份数 > 头奖份数**。原则：**钩子密度优先于钩子高度**。仅 `lottery_tiers` 场景适用。

### 权重规则

- **权重从场景档 `weight` 取**：默认档 {{CHANNEL_A}} ＞ {{CHANNEL_B}} ≧ {{CHANNEL_C}} ＞ {{CHANNEL_D}}、同级＝两家合计差额 ≤{{BUDGET_AMOUNT}}（不是精确等额）；`weight.enabled = false` 的场景（单渠道 / 积分制 / 平台奖励）整组跳过，不做权重分配。
- 平台充值卡按**各渠道历史参与人数**加权（默认档）；别的奖池模型不适用这条。
- **两个维度分开写清楚**，否则会出现「{{CHANNEL_A}} 单人实物成本 {{BUDGET_AMOUNT}}、{{CHANNEL_B}} {{BUDGET_AMOUNT}}」这种看着像错数的结果；并写明 {{CHANNEL_A}} 权重最高的依据（push 触达量级 / 资源置换力度）。

### 取价口径（5.5，别拿补贴价当成本价）

1. **不看截图上的到手价。** 电商页同时存在官方价 / 常卖价 / 30 天低价 / 大促价 / 国补价，截图抓到的往往是补贴后到手价（历史坑：某型号电商页补贴价与原价差距很大）。**基准取「常卖价 ~ 30 天低价」区间的上沿，再上浮 {{BASELINE_VALUE}}~{{BASELINE_VALUE}}**，补贴价、大促价不可复现。
2. **查证不能省。** 头奖档每一支至少做一次价格检索，记录区间，写进备选清单的「电商参考价」列。
3. **选品顺序：先在既定价带里挑，再谈升级。** 确实需要旗舰款时，单列「需加预算」备选并标明增量。
4. **资产三件套一次备齐**：名称（完整型号 + 配色）+ 图片 + 购买链接。缺图缺链的奖品不进最终方案。

### 改价三步复核（手工改数不复核必错）

改任何单价后：① 重算行总价值 → ② 重算渠道小计 → ③ **按场景档 channels[] 的个数**相加核对总盘子（不是固定{{CHANNEL_COUNT}}家）。

**CDK 类**（游戏内物品，成本低、相关性高，**但需 {{APPROVAL_PARTY}}审批**）：
SYANDANA批饰包 {{BUDGET_AMOUNT}}×50 · 幻离子霰弹枪与暮光调色盘 {{BUDGET_AMOUNT}}×{{BASELINE_VALUE}} · 入门武器组合包（含{{BASELINE_VALUE}}游戏内货币）{{BUDGET_AMOUNT}}×{{BASELINE_VALUE}}· Foxglove Syandana 礼包
- **CDK 核销率目标要查历史再定**：已大量发放过的库存码玩家持有率高，别直接拍 ≥{{BASELINE_VALUE}}（幻离子+调色盘已发放 3,{{BASELINE_VALUE}} / 剩余 6,{{BASELINE_VALUE}}）。

**分配原则：**
- CDK 走量（几十到几百份），实物做梯度——CDK 单位成本远低于实物且更贴合玩家
- **每档预留 {{BASELINE_VALUE}}款同价带替换品**，缺货时同档位换款，**不破价带、不改份数、不追加预算**
- **奖品只在正文保留一处总表**；换款时**三处同步**：正文奖品总表 / 奖品池备选清单（入选↔备选状态互转）/ 图片链接表。动手前先列清楚「谁进、谁退到备选池」

## 四、效果预估（口径已于 {{AS_OF_DATE}} 修订，见 context 第 6 节）

**定口径的第一原则：只设渠道实际能回传的指标。** 回传不了的（如 平台入库）不要写进目标表。

**预估口径清单从场景档 `metrics.comparable` 取，件数不是规定**（默认档：预约跳转 / 参与 / 加速环比 / 新进 / 回归 / 入库完成率 / 单客成本 / CDK 核销率；{{CHANNEL_E}}档含「一键入库人数」与 CPS 销量；{{PLATFORM_A}} 档是预约人数 / CTR / 下载激活）。下面列的是**默认档常见几项的算法定义**，换档按档内指标重写：

1. **活动参与人数** —— 按渠道自有口径，**不要求去重**
2. **加速人数环比（%）** —— 活动期 ÷ **活动前两周日均** − 1，各渠道分别算；**分母必须避开前置活动收官周**
3. **入库任务完成率** —— 完成「一键入库」任务的人数 ÷ 活动参与人数。**现行口径改为「页面点击率」**：点击率的分母（活动页访问）{{CHANNEL_COUNT}}家定义不一，且按钮放第几屏可直接操纵 CTR；入库完成率{{CHANNEL_B}}一直回传，历史 {{BASELINE_COMPLETION_RATE}}、中位 {{BASELINE_MEDIAN}}。证据等级 B 级 · 首期基线。
4. **回归人数** —— 渠道侧可算，单独报数

**曝光率（资源位曝光达成率 = 实际 ÷ 承诺）是履约层，不是效果 KPI**，别写进可比口径目标表。曝光/点击/PV/抽奖人次的绝对数为参考项，分渠道单列、不得相加。「入库人数」只在**所有渠道都回传不了**时才是禁用指标（{{CHANNEL_E}}能回传，就不是）。

**首次统计的指标必须标注「无历史基线，本期以建立基线为主」**——不要凭空给一个看似精确的目标值。

历史基线（用于校准，不要直接当目标）：
- {{CHANNEL_E}} H5：曝光 {{BASELINE_VALUE}}级 → 参与 {{BASELINE_VALUE}}级 → 入库 {{BASELINE_VALUE}} 级
- {{CHANNEL_B}}：曝光 {{KPI_REACH}}级 → 参与 {{BASELINE_VALUE}}级
- {{CHANNEL_D}}：曝光 {{BASELINE_VALUE}}级 → 参与 {{BASELINE_VALUE}} 级
- {{CHANNEL_A}}：曝光 {{BASELINE_VALUE}}级 → 参与 {{BASELINE_VALUE}} 级（转化偏弱，需复核）

⚠️ **{{VERSION_NAME_HIST}} 方案预估"参与 {{BASELINE_VALUE}}+"，四渠道可核对实测合计约 {{BASELINE_VALUE}}。**
缺口可能来自 {{CHANNEL_C}} 未计入或口径差异。**做预估时必须说明口径，不要把各家口径不同的数字直接相加。**

## 六、输出格式

