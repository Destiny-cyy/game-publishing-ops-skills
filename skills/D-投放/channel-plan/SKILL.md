# 渠道方案撰写

## 这个 skill 解决什么

把"这个版本要在哪些渠道做点什么"，写成**一份能拿去评审、能照着执行、能按同一口径验收的文档**。

它的价值不在创意，在**结构和口径**：
- 结构统一 → 不同节点、不同人写的方案可以横向对比，也能沉淀复用
- 口径统一 → 结案时不用再为"这个 {{KPI_REACH}}曝光算不算数"吵架

## 与相邻 skill 的边界（不要越界重复）

| skill | 管什么 | 不写什么 |
|---|---|---|
| `channel-selection` | **投哪些渠道**（打分、P0/P1/P2、kill 标准） | 不写方案正文 |
| **本 skill** | **方案文档怎么写**（结构、表达、逐渠道策略、口径与验收） | 不重新做渠道打分 |
| `launch-plan` | 时间轴与放行门（T-45/T-30/四层 gate） | 不定义方案模块 |
| `campaign-mechanic` | 单个活动的任务链与奖品包细节 | 不搭整体文档 |

工作流：`channel-context` → `channel-selection` → **本 skill** → `launch-plan` / `campaign-mechanic` → `campaign-retro`（回写基线）

## 开工前

必读：
- **`_shared/规则三层说明.md`——先选/建场景档**（第一输入）。渠道名单、平台能力、任务链、可比指标、奖池模型、价带、排期锚点一律从 `profiles/<id>.json` 取；本 skill 里「{{CHANNEL_COUNT}}家 / 四件套 / 与版本日同步 / {{BUDGET_AMOUNT}}~700 / T-45」都是默认档实例，不是必须满足的条件。
- **`_shared/REDLINES.md`** v2.0（尤其 0.1 自适应总则）——准则层唯一真源。本 skill 只讲"方案文档怎么写"，具体口径与奖品规则以准则 + 场景档为准。
- `_shared/context-template.md` 第 2 节（人群）、第 3 节（渠道台账）、第 5 节（预算）、第 6 节（口径）、第 8 节（约束）+ `../REDLINES.md` 第零章（硬红线清单）。

先确认六件事，缺一件就问，不要自己填（对应准则 10.1 开工前自检）：
0. **场景档选好了吗**：服线 / 节点性质 / 渠道名单与平台能力 / 预算模型 / 奖池模型。差异项写进 `overrides_log` 并说明理由。**没定档就动笔＝后面全按默认档套，返工率最高。**
1. **哪条服线**（{{SERVER_LINE_A}} {{PLATFORM_B}} / {{SERVER_LINE_B}} {{PLATFORM_A}}）——两套渠道池完全不同
2. **事实锚点**：版本名 + 上线日期 + 是否 {{DEVELOPER}} 主版本。**官方只给窗口没给日期的，写两套预案，不要把猜测写死**
3. **预算盘子**（总额 + 采买/奖励/素材怎么切）
4. **主目标是哪个**（新进 / 回流 / 声量 / CDK 售卖）——决定后面所有模块的取舍
5. **奖品四条约束**（价带 / 份数结构 / 权重 / 红线）——**必须在选品之前落地**，否则后面整张表返工

> 复盘结论（准则 8.2）：四版迭代里真正的内容返工只有两次，一次是事实锚点没核实，一次是奖品约束没先定。**返工不是写错，是开始得太早。** 顺序不能跳：事实 → 口径 → 目标 → 活动 → 奖品 → 排期。

## 一、渠道方案的九模块骨架（通用）

这是从 {{VERSION_NAME_HIST}} 方案、渠道工作总表、13 个节点的资源记录里反推出来的**真实结构**，不是教科书目录。九个模块，顺序固定，缺哪个要在文档里写"本轮不适用 + 原因"，不要默默删掉。

| # | 模块 | 该回答的问题 | 表达形式 | 常见错误 |
|---|---|---|---|---|
| 1 | **项目定位与目标** | 这个节点是什么、要什么结果、花多少钱 | 一段话 + 目标表（指标 / 目标值 / 口径 / 谁负责） | 只写"提升关注度"这种无法验收的话 |
| 2 | **人群与场景** | 主要打谁、他在什么场景下被触达 | 分层表（人群 / 规模 / 给他看什么 / 别给他看什么） | 只写人群不写"给他看什么" |
| 3 | **渠道组合与角色分工** | 每类渠道在链路里干什么 | 角色分层表（角色 / 渠道 / 为什么是它 / 合作形式 / 成本） | 渠道清单罗列，不分角色 |
| 4 | **逐渠道策略卡** | 这一家具体怎么做（本方案最核心的一节） | 每渠道一张卡：目标 / 内容形式 / 任务链 / 资源位 / 奖品包 / 节奏 / 主口径 | {{CHANNEL_COUNT}}家渠道用同一段话复制粘贴 |
| 5 | **节奏排期** | 什么时候上、上多久、节点怎么配合 | 时间轴（预热 / 爆发 / 长尾）+ 关键里程碑 | 只有上线日，没有预热和长尾 |
| 6 | **素材与人群配对** | 哪个渠道给谁看哪条素材 | 「渠道 × 人群 × 素材」三元组表 | 一条素材通投所有渠道 |
| 7 | **预算与奖品分配** | 钱和奖品怎么分到渠道 | 预算表（渠道 / 采买 / 奖励 / 素材 / 汇总）+ 奖品分配表 | 平均分，不按历史表现加权；**奖品表在正文与渠道章节各列一份**（两份必打架） |
| 8 | **转化路径** | 用户从看到到完成，中间有几步、每步损耗在哪 | 漏斗图（逐渠道）+ 关键流失点标注 | 只画漏斗不标流失点 |
| 9 | **效果口径与验收** | 最后怎么算做成没做成 | 口径表（指标 / 定义 / 来源 / 是否可比）+ 验收阈值 | 把不同渠道口径的曝光直接相加；写渠道回传不了的指标 |

**模块 4（逐渠道策略卡）是方案的核心**。其他八个模块都可以精简，这一节不能省——渠道差异全部落在这里。

## 二、渠道原型：七类，差异是硬差异

不同渠道不是"同一套打法换个名字"。完整差异矩阵见 `references/channel-archetypes.md`，这里给速查：

| 原型 | 本质角色 | 主口径 | 内容形式 | 节奏特征 | 成本 |
|---|---|---|---|---|---|
| **A {{CHANNEL_TYPE_A}}/工具类** | **转化基础设施**，不是媒体位 | 入库 / 加速 / 参与 | 客户端 banner+弹窗+加速页活动 | 跟版本日，活动期 7~14 天 | 资源置换，零采买 |
| **B 游戏社区&商城** | 转化 + 内容双担 | 入库 / CPS 销量 / 参与 | H5 活动 + 社区话题 + KOC | 最长，可跨预热到爆发 | 采买为主（大头） |
| **C 垂直媒体** | 声量与口碑 | 互动量 / 预约 / 阅读 | 论坛有奖互动（评论/点赞/晒图）、资讯 | 短频快，一波一话题 | 采买或置换 |
| **D 平台商店资源位** | 平台内发现与转化 | 预约 / CTR / 下载 | 轮播图、预约 H5、生态位 | 受平台排期约束，T+1 延迟 | 平台规则决定 |
| **E 信息流/效果广告** | 买量放大 | CTR / CPA / 激活 | 短视频、信息流素材 | 可随时起停，需冷启动 | 纯采买 |
| **F 网吧与内渠** | 场景铺量 | 启动量 / CPS | 客户端位、壁纸、网吧活动 | 长尾常驻 | 置换或低 CPA |
| **G 私域/社区** | 留存与回流 | 活跃 / 回流率 | 社群运营、公会、官号互动 | 日常持续，节点加码 | 人力为主 |

**关键判断：A 和 F 常被误当媒体位，其实它们是"转化链路本身"**——{{CHANNEL_TYPE_A}}解决的是{{SERVER_LINE_A}}最大的门槛（网络+入库），它给的是"能不能玩上"，不是"看没看到"。给这类渠道写方案时，任务链必须落到"入库/加速"动作上，只给曝光位是浪费。

⚠️ **E（信息流）在暂无实测数据**。写这类渠道时必须引用外部来源并标注，不得用 A/B/C 的实测基线套它。

## 三、执行流程（七步）

**Step 0 · 选场景档（最先做）**
`--list-profiles` 看现有档，选最接近的；差异大就新建继承 `base.json` 的档，只写差异项。
至少定：`service_line` / `node.type` / `channels[]`（含 capabilities 与 reportable）/ `budget.model` / `prize.model` / `metrics.comparable` / `schedule.needs_de_approval`。
**这一步决定了后面六步的所有参数**——跳过它，就等于拿默认档套所有活动。

**Step 1 · 定锚点**
节点名 / 上线日 / 服线 / 主目标 / 预算盘子，从场景档取或补进档。写进模块 1。目标必须是可验收的数字，不是形容词。

**关于上线日期**：方案内部按**内部排期口径**排期即可（例如"{{VERSION_NAME}} 版本日 上线"），但必须写明「对外物料发布前须与 {{DEVELOPER}} 官方公告复核」。官方没公布的日期，不得以既定事实口吻写进对外文案。

**关于活动时间（按 node.type 派生，不是固定「与版本日同步」）**：
- **版本周**：与版本日同步开跑（版本日 → +7 天）。上线周是自然流量峰值，奖品性价比最高。
- **预约期**：跟**预约开启日**开跑（{{VERSION_NAME}} {{ACTIVITY_WINDOW}}，版本日 版本日 另案不覆盖）；错位是设计，不是失误。
- **社区/平台型**：按平台排期或话题波次，H5 可跑 14~17 天，{{PLATFORM_A}} 轮播受 T+1 延迟约束。

写进场景档 `node.activity_window`。若因资源位冲突要错峰，在策略卡写明理由（例如 push 分两波）。**别把某一档的窗口写成通用结论。**

**Step 2 · 拉渠道角色**
从 context 第 3 节台账取渠道池（不要凭印象另拟），按 A~G 原型归类，写明每类的角色。写进模块 3。
若渠道清单来自 `channel-selection` 的打分结果，直接采用，不重新打分。

**Step 3 · 逐渠道写策略卡**（最耗时的一步，也是唯一不能套模板的一步）
每个渠道一张卡，按原型取差异化打法。字段固定：
`渠道 / 原型 / 本轮目标 / 内容形式 / 任务链 / 资源位清单 / 奖品包 / 起止时间 / 主口径 / 预估 / 依赖`
→ 详细差异与改写规则见 `references/channel-archetypes.md` 和本文第五节。

⚠️ **奖品只在正文保留一处总表**（准则 5.4）。逐渠道卡片只写活动形式与任务链，**不重复列奖品表**——维护两份必出现数字打架（历史坑：{{CHANNEL_B}}第二档单价 330 vs 319）。
卡片里的"奖品包"字段写成一句话指向总表即可（如「头奖 × 份 + 第二档 × 份，见奖品总表」）。**份数与权重从场景档 `weight` 取**：默认档是 {{CHANNEL_A}} ＞ {{CHANNEL_B}} ≧ {{CHANNEL_C}} ＞ {{CHANNEL_D}}、同级差额 ≤{{BUDGET_AMOUNT}}（`weight.enabled = true`）；单渠道 / 积分制 / 平台奖励场景该项关闭，不做权重分配，也别硬套「不平均分配」。

**Step 4 · 排节奏**
预热（T-14 → T-1）→ 爆发（T → T+7）→ 长尾（T+8 → T+21），**只是默认档形状**；按 `node.activity_window` 与平台排期改（预约期跟预约日、H5 跑 14~17 天、{{PLATFORM_A}} 有 T+1 延迟）。
每个渠道标注它**在哪一段是主力**：{{CHANNEL_TYPE_A}}在爆发段，社区跨全程，垂媒在预热段做话题。

**关键路径按依赖生成，不是固定两条**：
- `schedule.needs_de_approval = true`（涉及 CDK / CPS 新申请）→ 才有 **T-45 前提交 {{DEVELOPER}}**；走现有库存可绕开，但正文写明前提。
- 有资源位档期争夺 → 才有 **T-30 锁档期 + 书面承诺曝光量**；{{PLATFORM_A}} 档换成平台排期申请。
- 锚点清单从 `schedule.anchors` 取，别把别的场景的锚点搬过来。

若活动时间已写进头部与各渠道策略卡，模块 5 的时间轴表格可以省，不强制保留。

**Step 5 · 定口径与验收**
先把口径表写完，再写预估数字。

**定口径的第一原则：只设渠道实际能回传的指标。** 回传不了的（如 平台入库结果）不要写进目标表——写了验不了，还会逼出假数据。

**可比口径清单从场景档 `metrics.comparable` 取，不是固定四项**（{{AS_OF_DATE}} 修正：旧版本把「加速前一周环比 / 曝光率」写死在可比层，与准则 2.2、3.1 冲突）。

| 场景 | 可比口径 |
|---|---|
| 默认档（{{CHANNEL_COUNT}}家·预约期） | 预约页跳转 / 活动参与人数 / 加速人数环比（分母＝活动前**两周日均**）/ 新进加速 / 回归加速 / 入库任务完成率 / 单客奖品成本 / CDK 核销率 |
| `community_cps` | 一键入库人数 / CPS 销量 / H5 点击 / 单客成本 |
| `platform_resource` | 预约人数 / CTR / 下载激活数 |

判据只有一条：**该渠道确实能回传、且口径定义一致**。硬纪律不变：不可比口径（`metrics.noncomparable`）分渠道单列、不得相加、不得作结案依据；首次统计的指标标注「无历史基线，本期以建立基线为主」；每个渠道的预估必须标注它报的是什么口径；禁用指标带 `applies_to`，别全局一刀切（例：「入库人数」对{{CHANNEL_E}}有效、对{{CHANNEL_TYPE_A}}无效）。

**Step 6 · 风险与降级**
按 **依赖** 生成，清单存场景档 `schedule.risks`，条数不固定：
① 有 CDK 新申请 → 未批下来的替换奖品方案；② 有资源位/平台排期 → 档期冲突的备选位；③ 有跳转类指标 → **无法埋点的降级路径**；④ 有实物采买 → 缺货涨价；⑤ 预估与实测偏差的处理（**先对齐双方统计定义，再谈玩法调整，禁止直接改目标值**）。

**「版本延期预案」只在 `needs_version_delay_risk = true`（以版本日为时间锚点）时必写**——H5 可独立起停、社区话题按波次跑的场景不强制。别把「≥7 条风险」当验收标准。

## 四、输入 / 输出格式

### 输入

| 类型 | 内容 | 来源 |
|---|---|---|
| 必需 | 节点信息、服线、预算、主目标 | 用户口述或节点日历 |
| 必需 | 渠道台账、人群分层、历史基线 | `_shared/context-template.md` |
| 可选 | 渠道打分与分级结论 | `channel-selection` 输出 |
| 可选 | 历史节点实测数据 | 渠道资源记录.xlsx（按节点查） |
| 外部 | 行业报告、平台刊例、竞品打法 | **必须标注来源与年份** |

**证据分级（引用时必须标明等级）**：
- **A 级 · 使用方实测**：资源记录、工作总表、已执行方案 → 可直接引用
- **B 级 · 同品类类比**：{{BENCHMARK_GAME_C}} 在 {{PLATFORM_A}} 的 CTR 等 → 必须写"参考值，待使用方项目验证"
- **C 级 · 行业通用/外部报告**：必须写出处，且不得作为结案依据

### 输出

一份完整方案文档，九个模块齐全（不适用的写明原因），至少包含四张表：
1. 渠道组合与角色分工表
2. 逐渠道策略卡（每渠道一张）

## 五、避免"一套话术套所有渠道"（本节是硬要求）

### 五条反模式——见到就改

1. **同一段"活动形式"复制到各渠道（默认档是{{CHANNEL_COUNT}}家，别的场景可能是一家或七类）**
   {{CHANNEL_D}}的任务是"入库+首次加速"，{{CHANNEL_B}}是"关注+入库+加速达时长"，{{CHANNEL_E}}是"关注+入库+分享换积分"。
   → 任务链必须按渠道能力重写，不能共用一段。

2. **所有渠道都报"曝光 {{KPI_REACH}}"然后相加**
   {{CHANNEL_D}}报点击、{{CHANNEL_A}} 报 push、{{CHANNEL_B}}报 PV、{{CHANNEL_C}} 报抽奖人次、{{CHANNEL_E}}报入库——**口径不可比，不能相加**。
   {{VERSION_NAME_HIST}} 教训：方案预估"参与 6 万+"，四渠道实测合计约 3.4 万。缺口来自口径差异与 {{CHANNEL_C}} 未计入。
   → 每个数字标口径，汇总只用三个统一口径。

3. **奖品包平均分配**
   按渠道**历史参与人数**加权分配，不平均。{{CHANNEL_B}}、{{CHANNEL_D}}历史参与通常显著高于 {{CHANNEL_A}}。
   → 预算表要能看出"为什么这家多"。

4. **把{{CHANNEL_TYPE_A}}当广告位写**
   只写"首页 banner 曝光 XX 万"是浪费。{{CHANNEL_TYPE_A}}真正的杠杆是**加速福利**（渠道自有、不花钱、对用户是真价值）和**一键入库**。
   → {{CHANNEL_TYPE_A}}策略卡里，任务链必须落到入库/加速动作上。

5. **垂媒照搬效果渠道的 CTR 目标**
   垂媒的价值是话题与口碑，主口径是互动量/预约/阅读，拿 CTR 考核它没有意义，还会逼出标题党。
   → 每类渠道的主口径不同，考核指标不能统一。

### 逐渠道改写检查（写完策略卡后逐条对照）

- [ ] 七类原型里，本方案用到的每一类，**主口径都不一样**（不是同一套指标换个名字）
- [ ] 每一家的**任务链**是按它的能力写的，不是复制的
- [ ] 每一家的**内容形式**符合它的场景（客户端 banner / H5 / 论坛互动 / 轮播图 / 社群话题，各不相同）
- [ ] 每一家的**起止时间**不同——不是全部同一天开始同一天结束
- [ ] 每一家的**奖品包**按历史表现加权（顺序 / 同级容差从场景档 `weight` 取，不是每家均分 1 个）；`weight.enabled=false` 的单渠道 / 积分制 / 平台奖励场景不做加权
- [ ] 私域/社区型渠道标注了"先参与后发声"，没有直接发官方通稿
- [ ] 预估数字全部标了口径，没有跨口径相加
