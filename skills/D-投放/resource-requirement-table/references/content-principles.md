# 内容取舍原则与过往教训


> **本文件用到的占位符**（每个该填哪类信息、能不能外发，详见 `01-占位符字典.md`）
>
> | 占位符 | 该填哪类信息 |
> |---|---|
> | `{{COMMUNITY_VIDEO}}` | 文本 · 玩家讨论的**视频社区**名 |
> | `{{PLATFORM_A}}` | 文本 · 主投放平台名 |

## 一、角色术语先确认，别猜

涉及"品牌方 / 合作方 / 渠道方 / 平台方"这类词时，**先问清楚指谁再动手**。

典型业务模型：

```
品牌方（自家部门的品牌/市场团队）策划并出素材
      ↓
渠道侧（我方）收齐
      ↓
投到平台（{{COMMUNITY_VIDEO}} / {{PLATFORM_A}} 等载体）做宣传
```

曾经把"{{COMMUNITY_VIDEO}}"当成品牌方，整张表的方向做反了。宁可多问一句。

## 二、对外表只写"要什么 · 什么规格 · 怎么交付"

**写进精简表**：素材名称、素材说明、规格、数量、模板链接、关键规范、交付 DDL、交付内容（空列）、状态、备注。

**不写进精简表**（这些是我方内部推演用的，合作方懂业务）：

- 规则出处章节号
- 名额限制（如"每月最多 2 次"）
- 审核红线（血腥暴力、不引导其他平台等）
- 资格判定与申请通道
- 报备进度
- 规则背后的"为什么"

**教训**：写过一版带全部规则背景的表，被判"过于体系化、内容太多"；
删干净后又被判"过于简单"，补回模板链接和关键规范才合适。
平衡点在于**保留交付标准（尺寸/格式/硬条件），删掉推导过程**。

## 三、备注列只放对接人、链接、模板提示

不写"必填／可选"这类词（会被手动清掉），也不写"我方自产／品牌方提供"。

**对外表不刻意区分"我方"和"品牌方"——都是一起的。**
表格是协作工具，不是划责任的清单。

## 四、不另起行列

新增内容优先塞进**已有列**（如"备注"）或**已有说明行**，维持单区块、一眼能看完。
用户会手动删掉独立成块的附加区域。

对接入口、规则原文这类内容，要么并入说明行，要么按行挂进备注列，不要单独做一个区块。

## 五、全景表每条规则都要标出处

写成 `2.2①` `3.3` `4.2` 这样的章节号。被质疑时能直接翻原文对。
这条只在全景表做，精简表不做。

## 六、两张表口径必须一致

改全景表要同步精简表，反之亦然。曾经出现两边口径不一致，核对时反复返工。

## 七、用户定稿后不再擅自改

核查发现问题，报给用户，**由用户决定改不改**。
用户可能出于"对方了解业务"的判断选择不改。

## 八、★ 单元格只填结论，不填理由

**这是最容易犯的错，务必遵守。** 单元格要简洁明了，填**结论值**就够了。

### 日期格式

统一写「**11月2日**」：**不带星期、不带年份、不带理由**。

```
✗ 11/2（周一）｜配置前2周随报备提交     ← 有理由
✗ 11/2（周一）                          ← 有星期
✗ 11/2                                  ← 斜杠格式
✓ 11月2日                               ← 正确
✓ 10月30日 ★ 最早启动                   ← 唯一可加的：★ 优先级标记
```

### 理由去哪了

**为什么选这天、依据规则哪一条、有什么前置条件——在对话里告诉用户，不要写进表。**

星期几也不用写。用户自己会看日历；真正需要避开周末的是**排期时我该注意的事**
（如视频上架不支持周末/节假日），那是我在选日期时 internally 遵守的约束，
体现在选出来的那天本身就是工作日，不需要在表里说明。

### 例外：★ 优先级标记

只有一种情况可以加字：`10月30日 ★ 最早启动`。
判断标准：**去掉后会不会让人不知道这项不能拖**。会，就留；不会，就删。

### 其他列同理

规格列写 `1920×1080，≤500KB` 就够，不用解释为什么是这个尺寸。

## 九、常见内容坑

- **规格混写**：把"要什么内容""尺寸格式""易踩坑的硬条件"挤在一格。
  解决：拆成「素材说明 / 规格要求 / 关键规范要求」三列。
- **链接不可点**：长串文本里的 URL 不会被识别成超链接。链接尽量单独成格。
- **示例值被照抄**：示例一律加「（示例）」后缀。
