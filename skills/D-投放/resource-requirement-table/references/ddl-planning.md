## 🔴 第一原则：先分「直播前」还是「直播后」

**凡是需要从直播本身派生出来的素材（切片 / 录播 / 精彩剪辑 / 合集），
因果上只能在直播结束之后才存在，DDL 必须挂在 T 之后，不是 T 之前。**

真实教训（{{AS_OF_DATE}}）：第一版把视频素材和合集全排在 T-7（直播前），
用户当场纠正——「视频合集是得在直播结束后做成切片视频，才能有视频素材」。
这不是排期松紧问题，是**因果顺序错误**，排得再漂亮也是假的。

判断方法：问一句「这个东西在直播开始前，理论上能不能存在？」
答不能 → 挂 T 之后。

## 通用锚点（以 {{PLATFORM_A}} 3.0 直播与视频专区为例）

设 T = 上架 / 开播日。

### T 之前（倒推）

| 环节 | 提前量 | 依据章节 |
|---|---|---|
| 平台直播流邮件报备（{{COMMUNITY_VIDEO}}/{{COMMUNITY_VIDEO}}） | 无明文天数、**非即开即用** → 越早越好，标「★最早启动」 | 1.2② |
| 直播间入库确认 | 配置前 **1-2 周**；未入库需申请，流程 **3-7 天** | 1.2① |
| 非常态位报备（含活动简介+直播间地址） | 需运营 + 商店运营评定协商排期 → 约 **T-14** | 2.3① |
| 视觉定制素材（背景图 / 标题贴图 / TAB 贴图） | **申请通过后**才需要，留 1 周给 figma 蒙层 + 审核 + 返工 → 约 **T-7** | 2.3② |

关键点：定制视觉不是「报备时就交」，而是**申请通过后才开始做**。
报备和交素材之间必须留出评审时间，否则会出现"11/3 报备、11/6 就要交图"这种没时间做的排法。

### T 之后（顺推）

| 环节 | 时间 | 说明 |
|---|---|---|
| 切片源文件 / 封面 / 标题 / 作者信息 | **T+6** 左右 | 直播结束后切片制作约 3-5 天 |
| 视频站外链接 | 切片交付后 **+2-3 天** | 须**先在外站发布**才有链接；上架前 **1-3 天**给链接审核（3.4②） |
| 合集标题 / 封面 / Icon / 清单 | 再往后 **约 1 周** | 须视频**先逐个上架**才可整理成合集（4.3①） |

## 日历层面的硬约束

- **视频上架暂不支持周末 / 节假日** → 视频相关动作必须落在**工作日**
- **直播上下架支持定时、含周末 / 节假日** → 直播不受此限，**别和视频混为一谈**
- 报备评审类动作优先排 **周一/周二**，避开周五下午和周末
- 凡是"运营要评定 / 协商排期"的环节，不要卡着下限排，留 buffer

## 排完后必做的两项自检

1. **因果自检**：把每项按 DDL 排序，看有没有出现"东西还没产生就要交"的情况。
   （例如合集排在切片之前 ×）
2. **门槛自检**：有量化门槛的位置（如合集要求 ≥10 篇、单篇播放 ≥2000），
   确认按这个 DDL 交付时门槛能不能达到。达不到要把实际排期会被推迟这件事告诉用户，
   不要假装表上的日期就是上架日。

## 呈现方式

DDL 列不要只写日期，写「**日期（周几）｜为什么是这天**」。
一句话足够，例如：
- `10/30（周五）★最早启动｜{{COMMUNITY_VIDEO}}直播流须邮件报备开通，非即开即用`
- `活动结束后｜直播结束后完成切片制作`
- `12/3（周四）｜须视频先逐个上架方成合集`

给出理由是为了让填表的人知道哪个不能拖——尤其「★最早启动」那项，
它是整条链的瓶颈，晚一天后面全顺延。
